# Eval methodology

This document exists because "the eval says 6.1%" is not, by itself, a
defensible claim. A single number from a single run tells you almost nothing
about whether it would survive a different seed, a different reviewer's
questions, or six months of changes to the orchestrator. This is the
supporting material: what the number is measured against, what it does and
doesn't prove, what happens across other seeds, and where the pipeline's
known blind spots are - written down rather than left for someone to
discover.

It complements [`README.md#the-eval`](README.md#the-eval), which has the
headline numbers and the short version. This has the derivation.

---

## 1. Dataset generation

`data/generator.py::generate(count, anomaly_rate, seed, out_dir)` builds a
synthetic PO / GRN / Invoice / vendor-master / employee-master dataset from a
single `random.Random(seed)` instance. Nothing else in the module touches
randomness - no bare `random.choice`, no unseeded `random` module calls, no
reliance on dict or set iteration order for anything that affects an rng
draw. (`existing_skus = {l["sku"] for l in po["lines"]}` is the one set in
the file that could raise a hash-randomization flag; it's used only for O(1)
membership testing inside a comprehension over the fixed-order `PRODUCTS`
list, never iterated for the order of a random draw, so it doesn't affect
output even though Python randomizes `str` hashing per process by default.)

**Verified, not asserted.** `tests/test_eval_reproducibility.py` generates
the same `(seed, count)` twice, to two separate directories, in two separate
Python invocations, and diffs every output file (`pos.json`, `grns.json`,
`invoices.json`, `labels.json`, `vendors.json`, `employees.json`) **byte for
byte** - not "the same metrics came out," the literal same bytes on disk.
It also does this under `PYTHONHASHSEED` forced to a different value than the
default, specifically to rule out the hash-randomization class of
nondeterminism:

```
$ PYTHONHASHSEED=999 python data/generator.py --count 300 --anomaly-rate 0.2 --seed 42 --out-dir /tmp/a
$ python data/generator.py --count 300 --anomaly-rate 0.2 --seed 42 --out-dir /tmp/b
$ diff -rq /tmp/a /tmp/b   # no output -- every file identical
```

Result: **identical in every case tested.** No reproducibility bug was found
or needed fixing - the generator's discipline about routing all randomness
through one seeded `Random` instance holds up. (This was the one area of the
brief where I expected to find something and didn't; see §4 for what the
same exercise did find.)

The committed `data/` directory was generated with `--seed 42 --count 300
--anomaly-rate 0.2` and is not regenerated by a normal eval run - reproduce
it explicitly:

```
python eval/run_eval.py --regenerate --seed 42 --count 300 --anomaly-rate 0.2 \
    --data-dir data --out-dir eval_out
```

## 2. What's measured, exactly

`eval/run_eval.py` runs `agent.orchestrator.process_invoice` over every
invoice in the dataset against a `Ledger(fresh=True)` (so results don't
depend on what a previous run happened to leave posted - see the module
docstring for the bug this fixed) and compares each decision against
`labels.json`'s `expected_outcome`.

**A false clear** is an invoice `process_invoice` decided `auto_clear` on,
where the label says `expected_outcome: "escalate"`. Two denominators are
reported because they answer different questions:

- `false_clear_rate_of_cleared` - of everything auto-cleared, what fraction
  was actually wrong (precision-flavoured).
- `false_clear_rate_of_anomalies` - of every real anomaly seeded in the
  dataset, what fraction slipped through as a clear (recall-flavoured, and
  the number closer to what an AP lead actually loses sleep over - it's the
  headline number in the README for this reason).

**A false escalate** is the reverse: `process_invoice` decided `escalate` on
an invoice labelled `expected_outcome: "auto_clear"`.

**Escalation precision** is `genuine_escalations / total_escalations` - of
everything sent to a human, what fraction was a real problem. A dataset could
have 0% false-clear and still be useless if escalation precision were low
(a detector that escalates everything "wins" on false-clear rate and buries
the clerk in noise); reporting both together is what stops either number
being gamed on its own.

None of these are aggregated across anomaly types before being reported -
`confusion_matrix` and `per_anomaly_type_recall` break every metric out by
the 14 seeded anomaly types plus `clean`, specifically so a detector that is
excellent at 13 types and silently blind on the 14th can't average its way
to a good-looking headline. This is not a hypothetical: it's exactly the
failure mode the eval rebuild (see README) found in the *previous* version of
this eval, which reported one aggregate false-clear rate and no per-type
breakdown.

## 3. The cost-weighting parameter is a knob, not a finding

`cost_weighted_score = false_clear_count * fc_cost + false_escalate_count * fe_cost`,
default `fc_cost=50, fe_cost=1`.

**Be precise about what this 50:1 ratio is:** it is an illustrative
assumption chosen to make the false-clear/false-escalate asymmetry
inspectable as one number, not a measured or sourced constant. Nothing in
this project prices an AP clerk's ten seconds against a written-off duplicate
payment or a fraudulent bank-account redirect - those numbers depend on
transaction size, recovery rate, and a specific company's AP volume, none of
which this project has. Treat the **absolute** cost-weighted score as
illustrative only. The thing that *is* useful is the **ranking** it produces
across two runs or two configurations - "did this change move false clears
down at the cost of more false escalates, and was that a good trade at
roughly this ratio" - which is why `--fc-cost` / `--fe-cost` are CLI flags
rather than constants: change the ratio, re-run, and see whether a
conclusion survives a different assumption about how expensive a false clear
really is relative to a false escalate. If it only looks good at exactly
50:1, that's worth knowing too.

## 4. The 6.1% number: what it does and doesn't tell you

**What it is:** at `seed=42, count=300, anomaly_rate=0.2` (237 clean
invoices, 63 seeded anomalies of which 49 have `expected_outcome: escalate`),
3 of those 49 true anomalies were auto-cleared instead of escalated (all three
`threshold_splitting`): `false_clear_rate_of_anomalies = 3/49 = 0.0612`,
reported as 6.1%.

**Sample size.** 49 true anomalies is not a large sample, and a rate built
from a numerator of 3 moves in large discrete steps: one more or one fewer
false clear changes the reported rate by roughly two percentage points. A
95% Wilson confidence interval on 3/49 is roughly **2.1% - 16.5%**, wide
enough that "6.1%" should be read as "clearly not zero, plausibly somewhere
from the low single digits to the mid teens," not as a number with two
significant figures of precision. Quoting 6.1% without this interval, the
way the README's headline table does, is standard practice for a point
estimate but is not the same claim as "the true rate is 6.1%."

**Seed stability - the range, not just one number.**
`tests/test_eval_reproducibility.py::test_false_clear_rate_of_anomalies_stays_within_the_documented_range`
reruns the full eval (regenerate + score) at 8 seeds: `1, 2, 3, 42, 99, 123,
777, 2026`, all at `count=300, anomaly_rate=0.2`.

| seed | true anomalies | false clears | rate of anomalies |
|---|---|---|---|
| 1 | 49 | 4 | 8.2% |
| 2 | 49 | 3 | 6.1% |
| 3 | 49 | 3 | 6.1% |
| **42** | 49 | **3** | **6.1%** |
| 99 | 49 | 3 | 6.1% |
| 123 | 49 | 3 | 6.1% |
| 777 | 49 | 4 | 8.2% |
| 2026 | 49 | 3 | 6.1% |

**Range: 6.1% - 8.2%. Mean across the 8 seeds: 6.6%.** Seed 42, the one in
the README's headline table, now sits at the *low* end of the observed range,
tied with five other seeds at 3/49. That reverses what an earlier version of
this document said: seed 42 used to be at the high end, one of the two
worst-of-eight, which made the headline conservative. The change is not a real
improvement. Adding the `quantity_variance_no_grn` type to the generator
changed its random stream, so every seed now draws a different dataset, and
the ₹500-floor price-variance case that used to land at seed 42 now lands at
seeds 1 and 777 instead. Seed 42 is still not cherry-picked (it is the
project's long-standing default seed, used before this pass existed), but a
reader should know the headline number is now the optimistic end of the
observed spread, and the 8-seed mean, 6.6%, is the better single summary.
`true_anomaly_count` is exactly 49 at every seed (the largest-remainder
allocation in `scale_anomaly_plan` is deterministic given `count`/
`anomaly_rate` and doesn't depend on the seed; only *which* invoices draw
which anomaly does), so the denominator isn't part of the variation; only the
numerator moves, and by design it can only take integer values, which is why
the observed rates cluster at 3/49 and 4/49 rather than forming a smooth
distribution.

**The new type is caught at every seed.** `quantity_variance_no_grn` (3 per
300-invoice dataset) is escalated 3 of 3 times at all 8 seeds, with no false
clears and no false escalates. That is 24 cases in total, which is enough to
say the fallback works on this generator's shape of case and not enough to say
anything about real invoices.

Every false clear across every one of the 8 seeds traces back to one of the
two types already named in the README as structural, never a new type:
`threshold_splitting` (the retrospective-detection gap) or
`price_variance_out_tolerance` (the ₹500 floor edge case).
`tests/test_eval_reproducibility.py::test_false_clears_across_all_seeds_are_only_the_two_documented_structural_types`
checks this across all 8 seeds, not just 42 - the single-seed version of this
check already existed in `tests/test_eval.py`.

**What this range does and doesn't prove.** It's evidence the 6.1% figure isn't a one-off fluke in either direction - every seed lands in a fairly
narrow 6–8% band, not "2% at one seed, 30% at another." It is *not* evidence
about performance outside this generator's specific anomaly mix, invoice
volume, or the stub heuristic's behaviour - a differently-shaped dataset (a
different anomaly-type distribution, a different `anomaly_rate`, a live LLM
instead of the stub) could land somewhere else entirely, and nothing here
tests that.

## 5. A third structural blind spot, found by running more than one seed

The README documents two structural false-clear limitations (both discussed
above). Running the eval across 8 seeds instead of 1 - done specifically
because a single-seed report isn't defensible under questioning - surfaced a
**third**, on the false-*escalate* side, that the seed=42 report does not
show at all:

**`escalation_precision` is not actually 100% across seeds.** It holds at
6 of 8 tested seeds, but at `seed=2026` it drops to **97.9%** (46/47
escalations correct: one `vendor_name_drift` invoice escalates when its label
says it should auto-clear) and at `seed=777` to **93.8%** (45/48: three of
them).

**Root cause, traced exactly:** `agent/heuristics.py::normalize_vendor` (the
stub's deterministic vendor-matching logic) resolves two vendor-name strings
as the same entity when their `difflib.SequenceMatcher` ratio is at least
`VENDOR_SIMILARITY_THRESHOLD = 0.6`. Of the 10 canonical/alias vendor pairs
`data/generator.py::VENDORS` uses to seed `vendor_name_drift`, 9 score
comfortably above that threshold (0.74–0.93). One does not:

| invoice vendor | PO vendor | similarity |
|---|---|---|
| "Acme Corporation Pvt Ltd" | "Acme Corp" | **0.545** |

When the generator's per-slot RNG happens to draw the Acme Corp pair for a
`vendor_name_drift` anomaly (it did at seeds 777 and 2026, not at 42), the stub
heuristic correctly reports low confidence that the names match, and
`agent/orchestrator.py` correctly escalates a vendor match it isn't
confident about - that is the system working as documented, not a detector
bug. The mismatch is with the dataset's ground truth: `labels.json` marks
**every** `vendor_name_drift` invoice `expected_outcome: auto_clear`,
implicitly assuming the heuristic will always resolve every seeded alias
pair above its own threshold. One pair doesn't.

**Same shape as the other two documented limitations** (a labelling gap the
eval surfaced, not a bug in `core/matcher.py` or `core/anomalies.py`), so it
belongs alongside them rather than as a new category. Not fixed here -
lowering `VENDOR_SIMILARITY_THRESHOLD`, changing the Acme Corp alias, or
special-casing the label would all "fix" the number without fixing anything
real, and the whole point of this document is reporting what the eval finds
rather than tuning the dataset until the report reads clean (the README says
the same about the two generator bugs the previous pass found - see
"Building this eval also surfaced and fixed two latent bugs"). Pinned exactly
by `tests/test_eval_reproducibility.py::test_escalation_precision_is_not_actually_100_percent_across_seeds`,
which asserts the *precise* affected seeds and finding type, so a future run
that finds this at *more* seeds, or for a *different* type, fails loudly
rather than being absorbed into a vague "sometimes it's not 100%" tolerance.

**Practical implication:** the README's "Escalation precision: 100%" line
(and `tests/test_eval.py::test_escalation_precision_is_100_percent`) is true
at seed=42 specifically, not a general property of the system. See the
README's Known Limitations section for the same statement in the user-facing
doc.

## 6. The structural-vs-LLM decision boundary

`core/anomalies.py` marks each finding `needs_judgement: True` or `False` at
the moment it's constructed. `agent/orchestrator.py::process_invoice`
branches on finding type: `vendor_name_drift` and `suspected_duplicate`
consult `agent/tools.py::normalize_vendor` / `reason_duplicate`; every other
finding type (`missing_po`, all four three-way-match variance types,
`vendor_bank_detail_change`, `vendor_employee_collision`,
`new_vendor_first_invoice`, `approval_threshold_exceeded`,
`threshold_splitting`) goes straight to escalation without ever consulting a
provider - this is not a performance shortcut, it's the actual design claim:
these are facts (a bank account changed, a requester's invoices sum past
their limit), not judgement calls, and asking a model to bless a fact would
add a failure mode with no corresponding benefit.

That claim was, before this pass, enforced by convention - two independent
pieces of code (`core/anomalies.py`'s flags and `agent/orchestrator.py`'s
branches) that had to be kept in sync by whoever edited either one, with
nothing checking that they agreed.

`tests/test_decision_boundary.py` makes it checkable: one scenario per
finding type, each driven through `core.anomalies.classify()` directly (to
read the `needs_judgement` flag it actually assigns) and independently
through `agent.orchestrator.process_invoice()` with
`agent.tools.normalize_vendor` / `reason_duplicate` monkeypatched to record
whether they were called. The two must agree for every one of the 12 finding
types with a scenario, not just the 2 that are supposed to need judgement -
so a ninth finding type added later that claims `needs_judgement=True` but
whose orchestrator branch never consults a provider (or vice versa) fails a
test instead of silently shipping a trace that lies about what happened.

**The only two decisions where a model's answer can change the outcome:**

| Finding type | Provider consulted | What the model's answer can change |
|---|---|---|
| `vendor_name_drift` | `normalize_vendor` | Whether the vendor mismatch **auto-resolves** (same entity, confidence ≥ 0.6) or escalates. |
| `suspected_duplicate` | `reason_duplicate` | Severity, confidence, and wording on the escalation packet - **never whether it escalates.** A ledger near-match escalates regardless of the model's verdict; see §7 and `tests/test_duplicate_veto.py` / `tests/test_llm_veto_adversarial.py`. |

Every other finding type is a pure deterministic rule, by design and now by
test.

## 7. The duplicate veto: adversarial testing, not just the happy path

The one invariant this project cannot afford to regress: **a ledger
near-match on vendor + amount + date escalates as a suspected duplicate no
matter what the model says.** `agent/orchestrator.py` enforces this
structurally, not by a confidence comparison - `escalate = True` is set
unconditionally for any `suspected_duplicate` finding; the model's verdict
only ever adds an explanatory trace line, never gates the decision.

`tests/test_duplicate_veto.py` (pre-existing) proves the happy-path shape of
this: a stub scripted to answer a **well-formed** "not a duplicate, 0.99
confidence" still escalates. This pass added
`tests/test_llm_veto_adversarial.py` (20 tests) to go looking for ways a real
LLM endpoint could violate its own contract instead of just disagreeing
politely:

- **Malformed confidence values** - non-numeric strings, `None`, `NaN`,
  `+inf`/`-inf`, out-of-range numbers (999, -5), a boolean, an empty string,
  a list where a number was expected (10 cases).
- **Technically-valid-but-nonsensical JSON** - `is_duplicate` as the string
  `"False"` (truthy in Python, despite reading as false to a human),
  `related_invoice_id` as an integer, unexpected extra fields, an entirely
  empty response object, a JSON array where an object was expected.
- **The provider raising mid-call** despite `agent/llm.py::Provider.judge`
  being documented "must not raise" - a plain exception, a custom exception
  type, and (as a control) a slow-but-successful response via a scripted
  `latency_s`.
- **Everything broken at once** - `reason_duplicate` *and*
  `summarize_exception` both malformed on the same invoice, checking the
  veto doesn't have a hidden dependency on the summary succeeding.

**Result: every one of the 20 cases still escalates.** Nothing came close to
suppressing the veto - the unconditional `escalate = True` for
`suspected_duplicate` findings means the veto itself was never actually at
risk from any input shape.

**What *was* found, and fixed** (in `agent/tools.py`, not in
`core/vendor_master.py`, `core/approval.py`, or `core/chain.py` - outside the
files this pass was scoped to leave alone): two of the malformed-input cases
- a non-numeric `confidence` string, and `confidence: None` - **crashed
`process_invoice` entirely** before this fix, via a `:.2f` format spec on the
orchestrator's trace line that raises on a string or `None` rather than
misformatting it. Separately, a provider that raised mid-call (violating its
own documented contract) propagated an uncaught exception the same way. For
a batch eval, either failure mode is worse than "fail open" (a wrong
auto-clear) or "fail safe" (an unnecessary escalate) - it's **fail total**:
one bad response and the entire run dies, not just that one invoice. No
invoice was ever wrongly auto-cleared by this bug (the veto's own logic was
never bypassed), but a pipeline that dies on a single malformed response is
not a pipeline you can actually run against a live model with any confidence.

The fix: `agent/tools.py::_judge` now catches any exception a provider raises
and treats it as `Judgement.unavailable()` (enforcing the provider contract
defensively at the boundary rather than trusting each implementation to
honor it), and a new `_safe_confidence()` helper coerces whatever a provider
returns for `confidence` into a float in `[0, 1]`, defaulting rather than
raising on anything that isn't numeric. Both are minimal, boundary-level
fixes - no detection logic changed, and `tests/test_llm_veto_adversarial.py`
now pins the fixed behaviour down directly (it would have failed against the
pre-fix code on exactly the two cases above).

**Answering the brief's specific question - fail-safe or fail-open?** Before
this fix: neither: it crashed. After: fail-safe. Every adversarial case now
either escalates the finding (all `suspected_duplicate` cases, unconditional
by design) or falls back to the deterministic heuristic and proceeds
normally (cases that don't touch a `needs_judgement` finding at all).

## 8. Running the full claim-verification pass

```
# fast unit/integration suite (194 tests as of this pass, ~35-40s)
LEDGER_SENTINEL_LLM=stub python -m pytest tests/ -v

# just the eval_full marker: dataset reproducibility (byte-identical
# regeneration) + seed-stability (8-seed rerun) + cross-seed false-clear/
# false-escalate checks (~25s on its own)
LEDGER_SENTINEL_LLM=stub python -m pytest -m eval_full -v

# the adversarial LLM-veto boundary specifically
LEDGER_SENTINEL_LLM=stub python -m pytest tests/test_llm_veto_adversarial.py -v

# the structural-vs-LLM decision boundary specifically
LEDGER_SENTINEL_LLM=stub python -m pytest tests/test_decision_boundary.py -v

# regenerate the committed dataset and re-score it against the README's table
LEDGER_SENTINEL_LLM=stub python eval/run_eval.py \
    --regenerate --seed 42 --count 300 --anomaly-rate 0.2 \
    --data-dir data --out-dir eval_out
```

`eval_full` is a real pytest marker (`pytest.ini`), not a separate script -
it runs inside a normal `pytest tests/` invocation, so there is no way for
the fast suite to stay green while this slower, more expensive pass silently
bit-rots; select it on its own with `-m eval_full` when you specifically want
the claim-verification numbers rather than the full ~40s run.

## What this document is not

It is not a claim that Ledger Sentinel's false-clear rate is "6.1%, proven."
It's a claim that 6.1% is what one particular, reproducible, seed-42 run of
a specific synthetic dataset produces; that seven other seeds put the same
statistic in a 6.1%–8.2% range; that the sample behind any single seed's
number is small enough to carry a wide confidence interval; and that two
(now three, counting §5) specific, named gaps account for every false clear
observed across all eight seeds tested, with nothing swept under an average.
That is a narrower and more defensible claim than "6.1%" read on its own,
which is the point of writing it down.
